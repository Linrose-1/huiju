## 1. 第 24 项：活动免费特邀码

### 已确认规则

- 一人一码、单次使用；生成时绑定受邀人手机号，仅该手机号所属账号可用。
- 限生成时指定的活动；报名截止、活动结束或活动取消后失效。
- 报名成功才消耗；报名失败不消耗。取消报名不恢复原码，需要重新发码。
- 手机号核验使用账号经微信授权绑定的手机号，不使用报名表填写的联系手机号。
- 活动特邀码与建立上下级关系的会员邀请码是两种不同用途，不改变首次邀请关系。

### 本稿推荐方案（待确认）

1. **权限**：只有该活动发起人能生成和查看该活动特邀码；普通受邀者仅能校验、使用给自己的码。本期不增加平台代发或共同管理员。
2. **发放时机**：收费活动发布后、尚未截止且可报名时可以发码；草稿、免费活动、已取消／结束／下架活动不提供发码操作。同场活动、同手机号已有未使用有效码时直接展示原码，避免重复发放。
3. **资料门槛**：持码者仍需完成手机号、主动头像和名称后报名。特邀解决活动费用资格，不新增另一种付费会员身份；老板原文中的“非会员”不直接解释为本产品游客。
4. **下架再上架**：建议下架期间暂停校验和使用，恢复后若仍在有效期、未使用且活动未取消，则恢复可用。取消是永久失效，不与临时下架混同。
5. **记录**：成功报名显示“特邀免费”，发起人报名名单也显示此标签；普通收费报名仍提示联系发起人，不出现“已付款”“退款中”等支付状态。
6. **传递**：发起人手动复制“活动名称＋特邀码＋使用说明”发送给受邀人；本期不发送短信、不代用户发送微信消息、不把手机号放入公开分享内容。

### 页面流程

**发起人**：我的发起 → 活动管理 → 免费特邀码 → 填写受邀人手机号 → 生成 → 复制邀请文字。

管理页顶部保留活动名称；下方是发码入口、全部／未使用／已使用／已失效筛选。每行显示脱敏手机号、码状态、生成时间；已使用行可进入当前权限允许查看的报名记录。未使用码支持本人重新复制；本期不增加批量导入、批量发放及主动撤销。

**受邀人**：收费活动详情 → 立即报名 → 报名表“使用免费特邀码” → 输入并校验 → 显示“特邀资格有效，提交报名后生效” → 提交报名 → 成功页及我的报名显示“特邀免费”。

校验通过只是预检查，不提前占用名额、不消耗码。用户可移除已填码并按普通报名方式继续。提交时再次校验资格、活动状态和剩余名额；失败保留表单及码，不伪装成已成功报名。

### 面向用户的说明文案（待确认）

> 特邀码由活动发起人提供，仅限本活动及指定手机号本人使用。报名成功后获得本次活动免费参加资格；取消报名后原码不再可用。如有费用问题，请联系发起人。

发码区补充：“请输入受邀人用于微信授权绑定的手机号。特邀码不改变双方的学友邀请关系。”

### 状态与失败处理

| 场景 | 处理 |
| --- | --- |
| 首次进入／空列表 | 独立加载态；成功后无记录显示“还没有发放特邀码”及发码入口 |
| 游客操作报名 | 沿用完善资料流程，返回同一活动；不自动提交或消耗码 |
| 码错误／不属于当前手机号 | 清晰提示无法使用，不泄漏绑定的完整手机号或其他会员身份 |
| 已使用／已失效 | 对本人有权查看的码说明对应原因，不把失效状态当作网络失败 |
| 网络失败 | 保留手机号／码／表单，提供重试；不能默认恢复成普通收费报名后提交 |
| 重复点击／并发报名 | 禁用重复提交；服务端在同一事务完成报名和码消耗，保证只能成功一次 |
| 列表增长 | 服务端分页、触底追加；刷新和筛选重置，追加失败保留已有记录 |
| 已报名用户再次输入码 | 不追溯改写原报名资格；引导查看现有报名，避免重复报名 |

### 最小数据与服务设计建议

新增活动特邀码记录：所属活动、发起人、绑定手机号的受保护存储、码校验值、创建时间、已使用时间及关联报名；使用现有安全能力保护敏感字段，不把完整手机号或凭证写进日志。是否需要可恢复码用于重复复制，在实施时选定受保护的保存方式。

报名记录增加普通／特邀免费资格及引用，不新增支付流水。发码、列表、预校验、提交报名均由服务端核对所有权和身份；提交报名与消耗码共享事务。修改活动为免费等编辑场景须在实施前与现有编辑规则核对，不能暗中使已授予资格失效。需要新增迁移，但本轮不执行。

## 2. 第 25 项：活动详情图片

### 已确认规则

- 每场活动最多 3 张关联图片，详情顶部逐张横向滑动。
- 第一张为封面，上传时强制 5:4 裁剪。
- 第二、第三张不强制裁剪，在统一 5:4 区域内完整显示，可留边，不裁掉内容。
- 列表封面使用首张图片，列表展示区域不要求变成 5:4。

### 本稿推荐方案（待确认）

发起／编辑活动的“活动图片”区域显示三个图片位：封面、图片 2、图片 3。封面带“5:4 · 必须裁剪”标签；后两张标“完整展示”。已选图片提供替换／移除；点击首图可重新裁剪。为避免移动后隐式裁剪，本期不做拖拽排序，按图片位逐张管理。

封面裁剪页固定 5:4 框，支持移动和缩放，底部“取消”“使用此封面”。建议输出 1250×1000，比例强制、像素为清晰度建议；取消裁剪保留旧图。图片 2／3 选取后直接显示完整预览，不再弹强制裁剪。

详情页 1 张时不显示页码、不自动轮播；2～3 张显示“1 / 3”并手动滑动，建议不自动切换，方便看图。点击当前图进入大图预览，后两张使用原始比例。图片加载失败保持 5:4 高度并提供重试，不影响下方活动信息。

### 状态与兼容

| 场景 | 处理 |
| --- | --- |
| 已有单封面活动 | 继续按现有封面展示，不自动裁切或批量改写历史图片；再次替换封面时执行新规则 |
| 无图历史活动 | 延续当前无图表现，不补造图片 |
| 首图被移除 | 推荐仅清空封面位，不自动把第二张提升为封面；需重新选封面并完成裁剪后保存多图配置 |
| 已满 3 张 | 隐藏添加位，保留替换／移除，明确“最多 3 张” |
| 上传中／上传失败 | 对应图片显示进度或重试；未完成上传不能提交，其他表单内容保留 |
| 取消选择／取消裁剪 | 保留原已保存内容，不覆盖旧资源 |
| 退出未保存 | 沿用活动编辑页未保存提示；发布前预览与最终详情使用同一图片规则 |
| 后两张竖图或宽图 | 用 contain 完整显示于 5:4 容器，背景留边；不拉伸 |

### 最小数据与服务设计建议

当前代码以单个 `coverUrl` 为活动封面；保留它供列表、分享及旧客户端使用，增加有序活动图片集合，第一张与封面一致。服务端限制最多 3 张，验证资源所属、可用性及首图比例；编辑返回顺序明确，不能让客户端自行拼接其他用户素材。

现有单图自动作为兼容读取结果，不在本轮批量改写历史数据；迁移和最终存储结构在实施阶段核对。新增图片操作仅由有权编辑该活动的人执行，公开详情遵循现有活动可见权限。

## 3. 第 27 项：我的学友与人脉链路

### 已确认规则

- 我的学友显示直接邀请我的人、我直接邀请的人。
- 人脉链路展示多层完整路径，支持向上、向下及跨分支。
- 例如 D → C → B → E 可以作为查看路径；不会改变原来的 B 邀请 C、C 邀请 D、B 邀请 E 的事实。
- 不另建邀请体系，不改变首次有效邀请关系；名片字段仍受已有可见性控制。

### 本稿推荐方案（待确认）

**入口（已确认）**：在“我的”功能区仅增加“我的学友”；顶部显示“邀请我的学友”卡片，下方“我邀请的学友（数量）”列表。受邀列表分页、触底加载，点击人员进入对应名片。移除列表底部“查看人脉链路”按钮。空列表提示“还没有直接邀请的学友”，提供现有邀请码入口。

**查看某个人的路径（已确认）**：查看其他学友的名片时提供“查看我与 TA 的人脉链路”，以当前登录账号和该名片主人作为固定两端；移除独立人脉入口与搜索框。自己的名片不提供此入口。名片可从我的学友、活动名单等已有入口进入，故不局限于直接一层；无路径时说明暂无链路，返回仍是该学友名片。效果图补充名片入口局部，其他名片内容沿用现有设计，不据示例重做名片。

**路径页**：顶部明确“我 与 某某的连接”，中间为可纵向滚动的完整人员序列；每个节点展示当前有权查看的头像、名称，点击进入名片。每段关系写明“某某邀请了某某”，将查看顺序与实际邀请方向区分开。完整路径不按 3 层、5 层等任意层数截断，也不使用省略号冒充完整链路。

**长路径**：推荐服务端分段返回同一条路径并提供总节点数及后续游标，页面触底追加，明确“已显示 20 / 37 位，继续加载”；首尾身份保持可见。加载完成后才显示“完整链路已展示”，失败可继续重试，不能把未加载误写成无关系。

### 需要用户确认的重要边界

1. **平台根节点**：当前数据存在 `platform_root`。它是系统节点，不是自然人。建议不将其作为“邀请我的学友”，也不以共同平台根节点把所有自然进入用户包装成有私人关系；若两人唯一连接经过平台根节点，显示“暂无可展示的人脉链路”。这点影响实际路径口径，需用户确认。
2. **游客节点**：建议关系链可保留其连接位置，但未完成资料者显示“待完善资料的学友”，不展示微信身份或手机号；该节点不得被静默删除导致路径错误。是否允许游客本人查看链路，建议沿用现有会员功能门槛。
3. **路径隐私**：关系展示本身是新增能力，建议仅向当前登录会员显示“自己到目标会员”的路径，不开放任意 A 到 B 的关系查询，不提供整棵邀请树导出。
4. **无路径**：显示“暂未找到你们之间的学友邀请链路”，保留返回名片；不推测现实关系，不出现“无价值”“无贡献”等评价。

### 状态与最小服务设计

直接关系复用 `members.inviterMemberId`，不增加另一套上下级表。服务端查询本人直接邀请人及受邀列表，后者分页；路径计算基于现有邀请边，返回有权限的人员摘要与每段真实邀请方向。字段使用现有名片可见性规则，不返回手机号、微信号、二维码或未公开简介作中间节点信息。

加载、空列表、无路径、无权限、人员不可用、接口失败分别展示；人员资料不可见时保留匿名关系节点而非伪造断路。服务端应防止异常循环和重复节点；发现数据异常时说明无法完整展示，不能静默剪掉一段后宣称完整。
