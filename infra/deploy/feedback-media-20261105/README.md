## 获授权后的执行边界与顺序

1. 核对目标 `https://106.55.240.34:8443/api/v1`。用现有后台会话读取 `GET /admin/advertising/background`，确认 `imageId` 等于预期值并取得**当时**的 `version`；以 `PUT /admin/advertising/background` 提交 `{ "imageId": null, "version": 当时读取的版本 }`，沿用 Cookie、Origin、CSRF 校验。任何旧值不符或 409 都停止该项，不强行覆盖。保存通过既有服务产生审计，绝不删除历史背景图片。
2. 通过各活动原发起人的有效完整会员身份，读取 `GET /activities/:id/manage`，核对固定 ID、旧封面、当前完整图片列表及发起人归属。保存受控的变更前快照，避免包含凭据，不提交真实报名或会员数据。公开读取证据没有证明编辑资格、完整旧图片列表或活动仍处于可编辑时间，不能据此直接写。
3. 必须满足既有服务的生命周期约束：未开始、未结束、未取消且未下架。若活动已开始或不具备原发起人身份，停止该活动并单独报告；不得改时间、恢复活动、冒用身份或直写数据库绕过校验。三项可独立核对，不能因一项成功宣称全完成。
4. 使用该活动发起人的 `POST /media/covers` 上传 manifest 对应裁剪图、原图及所需后续图（`{ base64, mimeType: "image/jpeg" }`），仅采用真实返回 URL。上传成功也不等于活动已更新；失败时保留原活动，不自动删除旧资产。
5. 再读取并比对管理详情，确保业务字段及图片未被其他人修改。`POST /activities/:id/edit` 是完整表单：仅从最新详情提取 `ActivityWriteInput` 允许的现有字段，逐项保持原值（题目含 ID/顺序/选项/必填/公开标记），仅替换三项图片字段。`coverUrl` 等于 `imageUrls[0]`，`coverSourceUrl` 使用对应原图上传 URL；不能直接提交含输出字段的整个详情对象。接口没有版本锁，执行时需与活动发起人协调短暂暂停编辑；发现并发修改即停止，不覆盖。
6. 回读后台背景应为 null，公开背景 `GET /advertising/background` 应为 `{ "imageUrl": null }`；小程序重新进入“我的”确认 campus 图片。回读三活动管理/公开详情，逐项比较非图片业务字段未变，并检查 1/1/3 张、封面5:4、后两张完整显示和点击预览。回读名单数量/题目配置时仅核对必要摘要，不额外报名、签到或修改答案。
