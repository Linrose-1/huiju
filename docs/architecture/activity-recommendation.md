## 2. 处理流程与隐私隔离

2026-10-05补充：当前条件结构不表示“任选其一”。最新输入或当前条件所引用的最近原文包含“或／或者／OR／任选”等表达时，返回澄清并要求用户明确本次单项或同时满足的条件，不进入候选查询与排序，不计成功次数；不把多个备选主题静默改为同时必选。用户后续明确改为单项后可继续检索。这是有限文字保护，不等于支持任意自然语言析取或复杂逻辑检索。

1. 校验有效会员会话及完整资料、输入长度、请求幂等标识；短事务锁定本人的推荐额度并预留，事务结束后才调用模型。
2. AI将本次输入及用户主动提供的前文解析为结构化必选条件、偏好或矛盾问题。只传用户输入上下文与服务端提供的北京时间基准，不传会员档案、姓名、ID、邀请码或行为记录。
3. 服务端验证解析结构与原文依据。时间按北京时间解析成明确区间，日期省略或表达矛盾时展示理解结果或追问；明确必选条件不能因解析失败被删除。
   两阶段模型请求使用同一`gpt-5.5`，显式`reasoning_effort=low`以降低结构化解析／排序的推理开销；保持每阶段45秒超时与无自动重试。排序提示词明确偏好只影响排序、不得添加用户未提出的限制；服务端仍校验硬条件与公开引用，不因提示词变更放宽校验。
4. 活动领域查询先过滤可报名状态、本人发起和有效报名。时间、费用等结构化必选条件在服务端过滤；地点目前是自由文本，无城市编码或地理坐标，不能假定已经支持距离／行政区精确检索。无法可靠确认的地理条件需说明或追问，不静默忽略。
5. 站内仅提取本人允许用于匹配的资料与行为，通过词项重合等可解释方式形成辅助排序。辅助分不能恢复被必选条件排除的活动，也不能上传模型。该方法是首版建议，不新增兴趣标签填写要求。
6. 对候选公开信息做白名单投影，再交给AI评估主题匹配及简短理由。允许字段：临时候选标识、标题、介绍、地点、时间、免费／收费及金额；封面在站内用于展示，不需要交给模型。咨询联系方式、作者个人档案、报名名单与答案均不传。
7. 模型只能引用候选标识，返回推荐理由所依据的公开片段；服务端拒绝未知ID、重复ID、不在候选集的活动和无依据内容。个人资料辅助结果只影响站内排序，理由不能输出私密资料原文。
8. 固定本轮有序候选ID及理由，完成前再次检查活动状态。短事务确认预留仍有效、重新校验完成日额度，保存结果及成功计次，然后返回首批最多3条。

模型分两阶段处理是一轮检索的内部过程，不按模型调用数向用户扣额度；第二阶段失败则整轮不计成功。无候选可省略第二阶段，正常空结果计1次。内部阶段不是自动重试，任何失败均返回安全错误。

活动描述及用户输入是待处理数据，不能成为系统指令。使用结构化输出校验、候选集合和证据核对；AI不能执行报名、修改活动或查询任意会员数据。用户输入本身可能含个人信息，应提示避免填写无关敏感信息，并避免请求体与模型原文进入普通日志。

### 候选规模

不允许先截取最新若干条再声称“全平台无匹配”。实际先在SQL中筛选状态与明确时间、费用、地点、主题文字，再查询至多61条用于判断是否超过60条预算；公开投影JSON同时限制60000字符。超预算返回澄清，不计成功，不截断正文或声称全库无匹配。当前不分块调用模型。

每阶段模型超时45秒，两阶段至多90秒；数据库预留120秒，小程序请求100秒，不自动重试。对话最多12条、每条2000字符、总计8000字符。解析对费用、否定、基础日期与无法可靠支持的限制提供确定性保护，但不宣称正则能够理解任意自然语言；模型质量仍需后续真实调用验收。地点／主题以明确原文片段匹配，不支持距离、价格区间或人数条件；这些条件需澄清。

## 3. 额度、幂等和分页

- 推荐每天10次与草拟每天5次分账，按成功完成时北京时间自然日裁决。失败、超时和过期结果不计成功；正常空结果计成功。
- 每会员一个有效预留，使用随机标识和到期时间；旧调用失败清理时只能删除自己的预留。完成时重新锁定、检查当日成功次数，避免跨进程及跨日超额。
- `requestId`绑定会员与本次输入摘要，同标识同内容可回读完成结果，不重复调用或计次；同标识不同内容返回冲突。响应丢失时重试同标识；确定失败后用户重试新尝试，不自动循环调用。
- 初次检索返回`searchId`及不透明游标。分页只读取服务端保存的有序结果，禁止客户端提交活动ID列表、排序或计次状态作为事实。
- 每页最多3条；下架、已报名等实时不可用项跳过并继续扫描固定序列补足，游标按已扫描位置推进，不以返回数量简单递增。相同游标重复请求不产生重复展示记录；客户端按ID去重。
- 查询快照过期与无结果分开提示，不自动重新调用模型。达到每日限额仍可读取未过期的已有结果；过期后可查看已打开的真实活动详情或普通列表。
- 矛盾澄清／候选过多不计成功。实际每会员60秒最多6个新尝试（包括失败／澄清），每会员仅一个有效数据库预留，单进程至多4个处理中请求；技术限流返回`SEARCH_BUSY`，不伪装成每日额度耗尽。
- 结果保存生成时公开字段的SHA256指纹。模型返回后和每次取页均核对当前活动字段与可报名状态；内容变化的活动跳过并继续扫描补足，避免使用旧理由推荐已不满足条件的活动。

## 4. 数据结构

新增schema及`0009_activity_recommendations.sql`迁移仅生成并静态审阅，本轮没有连接或迁移现有库。已有迁移必须按journal顺序处理；不得只复制SQL绕过既有迁移状态。新表均为附加结构，无既有业务列删除或回填；回退应用版本时可暂时保留新表，删除新表属于独立授权操作。

| 拟新增表 | 最小职责与关键约束 |
| --- | --- |
| `activity_recommendation_searches` | 查询ID、会员、requestId、输入摘要、状态、创建／完成／到期时间、结构化条件及有序结果JSON；唯一`member_id + request_id`，索引`member_id + completed_at`；成功状态用于10次账本，清理结果载荷不能删除仍需计次的成功事实 |
| `activity_recommendation_reservations` | 会员主键、预留标识、requestId、开始／到期；跨实例抢占与旧结果隔离 |
| `activity_recommendation_events` | 查询、活动、会员、展示／查看事件、时间及幂等键；只记录校验过的归因，不存原始提示词或会员资料 |
| `activity_recommendation_conversions` | 真实报名操作ID、查询／活动／会员、直接查看来源、时间；报名操作唯一，响应重试不重复计转化；取消后再报名是新的真实操作，不覆盖历史 |

本次对话文本建议仅保存在绑定身份的客户端内存，服务端只在处理时使用；结果快照与条件用于当前会话分页，不提供历史列表接口。成功计次与最小效果事件需要持久化，不能用进程内计数冒充MySQL事实。

“本次会话”按独立页面实例生命周期实现：去详情／资料页产生`onHide`时保留，关闭独立页面产生`onUnload`时结束；再次从入口进入新建会话。未确认响应的检索在返回后由用户手动重试同一requestId；卸载与换号丢弃迟到响应。服务端保留统计事实不提供历史会话访问。

**已确认的数据生命周期（2026-10-02）**：结果及直接来源有效期30分钟，效果明细保留90天，原始对话和模型原文不落库。实现提供明确的清理入口，不新增任务系统；执行真实数据库清理仍需核对目标和授权。

读取在30分钟到期后立即拒绝结果和归因；物理清理由显式维护入口`apps/api/scripts/recommendation-cleanup.mjs`调用记录模块执行，清除过期条件与结果载荷，并按90天保留效果明细。它不自带调度，本轮未执行；环境启用时需明确清理安排，见[脚本说明](../../scripts/README.md)。清理保留当天计次事实，不因结果过期重新执行原幂等请求。

## 5. 接口契约

路径基于`/api/v1`，均要求有效会员 Bearer 与完整资料；无会话返回401，游客会话资料不完整返回 `PROFILE_INCOMPLETE`。写操作用POST兼容小程序。Controller/DTO已生成OpenAPI及客户端类型，字段详见[API说明](../api/README.md)。

| 方法与路径 | 输入／响应要点 |
| --- | --- |
| `POST /ai/activity-searches` | `requestId`、本次用户消息及本会话用户输入上下文；返回结果或澄清问题、理解条件、`searchId`、最多3条、游标、`hasMore`、当日剩余次数；模型不得接收从档案推导的条件 |
| `GET /ai/activity-searches/:id?cursor=…` | 验证查询归属和期限；返回后续最多3条及实时可用状态，不调用AI、不计次 |
| `POST /ai/activity-searches/:id/impressions` | 当前页实际展示的活动ID及幂等标识；必须属于已下发结果，不能把全部候选或返回但未展示的行计作展示 |
| `POST /ai/activity-searches/:id/views` | 推荐卡片进入并成功加载详情后确认查看；验证展示、身份、活动，返回与本次直接流程绑定的不透明来源凭据 |
| 既有报名POST扩展可选来源 | 只用于归因，服务端验证会员、活动、展示／查看、期限；保持原报名完整度、状态、容量及答案校验 |

来源无效、过期或统计失败不能被用作绕过报名的理由。建议无效来源降级为普通报名，不产生转化；数据库故障若导致报名事务失败，应显示真实失败，不能先报告成功再丢业务事实。未登录、字段无效、额度耗尽、正在处理、查询过期、模型超时／失败、输入冲突使用稳定安全错误码。

## 6. 直接归因与模块关系

推荐模块编排查询和模型；活动模块公开可报名候选查询，身份／阅读模块公开最小辅助数据查询。不得由推荐控制器直接写报名表或从完整会员DTO拼模型请求。

建议将额度／事件及转化写入放入不依赖活动业务服务的推荐记录模块；推荐编排模块和活动模块均可依赖它，避免`ActivitiesModule ↔ AiModule`循环。报名事务由原`ActivityService.write`拥有，通过记录模块公开方法，在同一事务写入已验证来源与真实报名操作的关联。模块不各自另开事务破坏原子性。

直接来源沿“推荐卡片→该详情→该报名表→必要的资料完善→原报名表”传递并由服务端验证。只在当前流程内存保存，不写持久化导航缓存；普通列表、通知、扫码、分享和其他活动详情入口不继承它。所有分享路径明确剔除查询ID和来源凭据，保留原邀请码规则。

事件及报名归因统一按活动→会员→查询→事件的顺序取锁，批量活动按ID排序，避免外键检查造成反向持锁。额度事务只锁会员、预留与查询，不持活动锁；模型调用在事务外。维护清理分步自动提交，不跨五表持有同一个事务；各步幂等，部分失败可以重跑。以上锁序有代码与替身回归，真实MySQL多连接行为仍未验证。

查看凭据必须绑定当前会员、活动、推荐查询及失效时间；客户端参数本身不是可信归因证据。即使无来源也不妨碍原有报名。不能用“最近看过推荐后曾报名”替代本次直接来源。

归因细化建议：只记录实际发生的首次／重新报名操作，已经有效报名的幂等返回、取消或修改答案不新增转化；多次点击时采用当前报名表实际携带且验证通过的直接查看凭据，不做全局最近触点推断。“已报名排除”建议按当前`active`状态处理，已取消者可重新竞争名额。重新报名如何在运营报表中去重仍未确认，不在本轮预建报表。

## 7. 页面承接与状态

已新增`pages/assistant/activity-search.vue`，在`pages.json`注册原生标题。独立内存会话保存用户输入、显示对话、条件、当前查询、分页和来源；绑定会员及API环境，身份过期／换号清空私密结果，旧请求不能写入新会话。可见卡片由IntersectionObserver确认展示，卡片点击补报曝光，全部候选不自动计展示。

2026-10-19 最新已确认规则（实现待验证）替代旧仅登录返回目的：找活动统一使用 `requireProfile`，游客操作时进入完善页，三项完整后返回原上下文；静默身份本身不授予检索资格。原仅会话兼容参数不能绕过新门槛。

当前`member/profile.vue`保存后只提示成功，尚无自动返回契约；实现可保留页面栈返回并保留推荐页面实例，若增加“保存并返回”则限定在推荐入口上下文。`finishProfile`目前只核对`id/edit`，新增来源参数后需核对推荐上下文，防止同一活动不同来源被错误合并。实际拟改范围还包括活动详情读取来源、构造报名目标，报名表读取／提交来源，以及服务层DTO和生成客户端；不能只新增找活动页面就宣称全链路完成。

| 状态 | 页面行为 |
| --- | --- |
| 未识别／会话失效 | 静默恢复，游客操作时补全；完成后回原找活动页，取消回浏览入口，不能循环跳转 |
| 完整会员、首次无输入 | 输入框、简短示例，不自动消耗次数 |
| 检索中 | 禁止重复提交，保留本次输入；离页／换号隔离迟到结果 |
| 有结果 | 展示理解条件、最多3卡片、理由和偏好差异；可继续输入或查看更多 |
| 资料缺少辅助信息 | 不阻断，轻引导去完善；返回保留结果，不自动重新检索 |
| 澄清／无匹配 | 清楚说明差异；只有用户修改条件才重新检索 |
| 追加失败／无更多 | 保留已加载内容，明确重试／无更多，不偷偷从第一页重来 |
| AI失败／额度耗尽 | 保留输入和已完成结果，明确状态及可用动作；不自动重试 |

具体视觉按既有助手及活动卡片风格实现，不新增未经确认的高保真设计承诺；本方案仅确定结构与交互，视觉／微信工具验收后置。

## 8. 实施顺序与验证

1. 数据及领域契约：明确生命周期配置，增加schema、短事务额度、候选查询和推荐记录模块；生成并审阅迁移，不自动执行。
2. AI与API：结构化解析、候选公开白名单、理由证据、结果快照与分页，补幂等／错误／跨日／隐私测试；生成OpenAPI和客户端。
3. 小程序：两个入口、游客补全返回、对话结果页、资料返回及分页状态；补页面脚本行为回归。
4. 归因：卡片展示／详情查看／报名事务与来源传递，覆盖伪造、分享、普通入口、重复提交、资料返回及重报。
5. 工程收口：完整`corepack pnpm verify`；代码／配置／资源改动完成时更新当月实现日志与状态索引。

L1覆盖隐私载荷、必选与偏好、不确定条件、可报名过滤、每批3条、稳定游标、模型失败、成功空结果计次、响应丢失、10次上限、跨日和身份竞态。安全替身只能证明逻辑，不证明真实模型质量或MySQL锁行为。

L2需单独授权的隔离MySQL迁移和多连接额度／归因原子性验证；前端人工验收按用户安排后置。L3真实模型费用、真实微信和真机、部署分别验证。本文不授权执行迁移、付费调用、依赖安装、Git写操作或部署。
