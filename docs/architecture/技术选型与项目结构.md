# 会聚｜技术选型与项目结构

状态：首期技术基线 v2  
日期：2026-09-25  
依据：[首期 PRD](../product/首期PRD.md)与[小程序框架与导航](../product/小程序框架与导航.md)

本文确定首期开发使用的技术底座、应用边界和目录结构。产品规则仍以 PRD 为准；尚未确认的业务细节在对应功能设计时补齐，不阻塞工程框架建立。

## 1. 总体结论

首期采用 **pnpm workspace 单仓库 + 模块化单体 API**：

- 微信小程序：uni-app、Vue 3、Vite、TypeScript、Pinia。
- 管理后台：Vue 3、Vite、TypeScript、Vue Router、Pinia、Element Plus。
- 服务端：Node.js 24 LTS、NestJS、TypeScript、REST API、OpenAPI。
- 数据库：MySQL；Drizzle ORM 管理类型化查询和可审查的 SQL migration。
- 文件：本次最小链路按 2026-09-26 用户确认先存本地；原素材及映射放 `docs/资源`，小程序运行素材放 `static/huiju`，会员头像由 API 本地受控目录保存。S3 兼容对象存储作为后续方向，本次不接入。
- AI：服务端统一的 AI provider 接口；具体模型和供应商通过环境配置选择。
- 部署：Docker 镜像；首期按 API、管理后台、MySQL、对象存储等独立进程部署。云厂商待定，不写入业务代码。

系统先保持一个 API 服务和一个 MySQL 数据库。当前规模不需要微服务、消息队列、搜索集群或独立推荐服务；出现可测量的性能或运维压力后再拆分。

## 2. 选择理由

### 小程序继续使用 uni-app

现有 `frontend/` 已是 uni-app 工程，设计稿和导航也以微信小程序为目标。改用原生小程序会产生一次没有明确收益的重写。新业务代码统一迁移到 Vue 3、Vite 和 TypeScript，不继续使用当前模板的 Vue 2 兼容分支。

### 管理后台使用独立 Vue 应用

后台与小程序的导航、组件和权限体验不同，独立应用更清楚。两端通过同一 API 和生成的 TypeScript 客户端共享接口契约，不直接共享页面组件。

### 服务端使用 NestJS 模块化单体

首期已经包含身份、活动、报名、权限、通知和 AI 等多个业务域。NestJS 的模块、依赖注入、Guard 和 OpenAPI 支持适合把边界写清楚，同时仍以一个服务部署，控制复杂度。

### MySQL + Drizzle ORM

活动、报名、邀请关系和权限数据具有明确关联及事务要求，采用关系型数据库 MySQL。Drizzle 用 TypeScript 定义 schema，同时生成可审查的 SQL migration；并发名额、重复报名和邀请关系通过事务、唯一约束及条件更新保证。

数据库引擎决策记录见 [ADR-0001](../adr/0001-primary-database-mysql.md)。

## 3. 运行与版本策略

- Node.js：固定 24 LTS 主版本；开发机当前为 `v24.14.0`，符合基线。
- 包管理器：pnpm workspace；根 `packageManager` 已固定为 pnpm 12.6.0。
- TypeScript：所有新应用启用严格模式。
- 依赖版本：建立应用骨架时依据当天官方稳定版本写入 lockfile；本文件不提前虚构具体版本号。
- 环境变量：仓库只提交 `.env.example`，密钥、AppID、数据库地址和 AI 凭据不入库。

## 4. 应用与模块边界

### `apps/miniapp`

面向会员的微信小程序。负责页面、交互、微信能力调用和本地状态；不在客户端决定权限，不直接访问数据库或 AI 服务。

页面按业务能力组织：活动、助手、我的、身份补全和共用页面。`pages.json` 是原生导航标题和 tabbar 的唯一配置源，页面内容区不重复原生标题。

### `apps/admin`

面向平台管理员的 Web 后台。首期负责会员查询、活动查看与处置、活跃度、导出和运营文案配置。

### `apps/api`

唯一业务 API。建议从以下模块开始，只有实现对应功能时才创建代码：

- `auth`：微信身份、后台登录、会话。
- `members`：会员、资料、公开设置、邀请关系。
- `activities`：活动、状态、分享信息、评论与点评。
- `registrations`：报名、问题答案、容量控制、签到。
- `analytics`：浏览、转化和活跃度统计。
- `notifications`：小程序站内通知。
- `content`：活动页和助手页运营文案。
- `ai`：活动草拟和活动推荐的 provider 适配层。
- `admin`：后台专用查询与管理命令。

权限校验放在 API 的 Guard 和业务服务中。客户端隐藏按钮只改善体验，不作为授权依据。

### `packages/api-client`

由 API 的 OpenAPI 文档生成，供小程序和管理后台调用。生成代码不手工维护，避免三端各写一套请求和响应类型。

### `packages/shared`

只放不依赖 Vue、NestJS 或数据库的纯常量和少量跨端类型，例如活动状态展示值。数据库实体、服务端权限规则和页面组件不得放入此包。

### `packages/config`

集中保存 TypeScript、ESLint 和格式化等工程配置。它不保存环境变量或业务配置。

## 6. 数据与接口约定

- API 前缀使用 `/api/v1`；首期使用 REST，不引入 GraphQL。
- MySQL 是业务事实源；小程序缓存不得作为报名、人数或权限的最终依据。
- 报名占位、取消释放名额和最后一个名额竞争必须在数据库事务中完成，并由唯一约束或条件更新兜底。
- 业务时间在数据库保存 UTC 时间点，接口使用 ISO 8601；界面按中国时区展示。
- 主键使用服务端生成的 UUID；邀请码等对外标识另设字段，不把手机号、微信标识或群名作为业务主键。
- OpenAPI 是前后端接口契约源；客户端由它生成。
- 本次图片使用本地打包资源或 API 本地头像目录，数据库保存受控访问路径；后续对象存储接入另行确认。
- 操作日志至少覆盖管理员下架/恢复、隐藏内容和运营文案修改。

## 7. 测试基线

- 小程序和后台：类型检查；对状态转换、表单校验和权限相关展示写有意义的单元测试；核心流程做页面级测试。
- API：模块单元测试与数据库集成测试；报名并发、邀请关系固定、资料权限、活动状态变化必须有集成测试。
- OpenAPI：`corepack pnpm api:check` 从源码构建后以临时产物检查接口与客户端漂移；完整 `verify` 已纳入检查。当前尚未配置 CI，后续接入时复用该命令，不将本地检查写成 CI 已通过。
- 真机验证与自动化测试分别记录；自动化通过不代表微信分享、手机号授权或朋友圈入口已经真机通过。

按文件范围预览建议检查使用 `corepack pnpm verify:plan <文件...>`，只输出计划；完整验证与命令副作用见[验证与验收](../testing/README.md)。目录中的业务模块按实现需要创建，不为检查工具预建空模块。

## 8. 暂缓决定

以下内容不影响建立代码框架，等外部条件明确后再定：

- 云厂商、域名、备案、证书和最终容器运行环境。
- 对象存储供应商。
- AI 模型和供应商；先遵守统一 provider 接口和数据最小化原则。
- Redis：首期默认不引入；只有限流、短期验证码、分布式锁或热点缓存出现真实需要时增加。
- 异步队列、全文搜索、微服务和数据仓库。

## 9. 现有 `frontend/` 的处理

原 `frontend/` 是 HBuilderX 生成的 uni-app 示例工程。其页面入口、静态资源和 `uni_modules` 已迁入 `apps/miniapp/`，并转换为 Vue 3/Vite/TypeScript CLI 结构。迁移完成后，原目录已移除。
