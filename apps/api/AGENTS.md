# API 协作规则

本目录继承仓库根目录 `AGENTS.md`，并补充 NestJS 模块化单体约束。

## 模块与数据所有权

- 使用 NestJS、TypeScript、MySQL 和 Drizzle ORM。
- Controller 只处理协议、认证上下文和输入输出映射；业务规则放在对应模块的应用服务或领域服务中。
- 每个模块拥有自己的数据写入规则。跨模块操作调用公开服务，不直接更新其他模块的数据表。
- 注册名额、重复报名、邀请关系和关键状态流转使用数据库事务、唯一约束或幂等键保证并发正确性。
- 业务动作使用明确方法表达，例如报名、取消、审核、发布；避免在调用方散落任意字段更新。

## API、权限与错误

- 每个受限接口在服务端重新校验身份、角色、资源归属和资料完整度。
- DTO 验证所有外部输入；响应 DTO 和 OpenAPI 契约不泄漏数据库内部字段。
- 错误响应使用稳定业务码、可理解消息和关联请求标识，不返回 SQL、ORM 异常、堆栈或密钥。
- 改动接口契约后同步 OpenAPI 产物和 `packages/api-client`，避免手工维护多套类型。

## 数据库变更

- Schema 变更必须通过 Drizzle migration 留痕并人工检查 SQL。
- 未经明确授权，不运行迁移、不执行 `db push`、不写共享数据库，也不做破坏性数据修复。
- 迁移设计应提供回滚或前向修复路径；删除列、收紧约束和数据回填需单独评估现有数据。

## AI 与外部服务

- 模型调用集中在 `ai` 模块的适配层，业务模块依赖明确接口。
- 发送给模型的数据遵循最小必要原则，排除手机号、真实身份标识和无关私密资料。
- AI 输出只能作为候选内容；写入关键业务状态前必须经过确定性校验或用户确认。
- 外部服务的超时、失败和费用边界要显式处理，不把供应商响应直接暴露给客户端。

## 验证

- 依赖可用时，运行 `pnpm --filter @huiju/api type-check`、相关测试和必要构建。
- 业务规则优先用聚焦单元或集成测试验证；并发和约束依赖真实 MySQL 行为时，不用纯 Mock 代替。
- 单元测试、集成测试、本地数据库、外部服务沙箱和生产环境分别记录证据。
